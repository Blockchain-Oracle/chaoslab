## 1. The 400-line file rule — enforcement mechanism

Abu's hard constraint: every code file in ChaosLab must be ≤400 lines and the limit is enforced in CI, not as a guideline. The mechanism differs by language because ruff (the natural Python choice) does **not** ship the file-level rule.

### 1.1 Python — the truth about ruff and PLC0302

Important finding, verified across multiple sources:

- Pylint has a rule `C0302 too-many-lines` (module-level) with default `max-module-lines = 1000`, configured via `[tool.pylint.format] max-module-lines = 400`.
  - Source: https://pylint.readthedocs.io/en/stable/user_guide/messages/convention/too-many-lines.html
- **Ruff does NOT implement an equivalent of pylint's `C0302`** as of v0.15.x.
  - The Pylint convention (PLC) family in ruff is partial. Tracking ticket and rule index confirm `PLC0302`/`too-many-lines` is not in ruff.
  - Source: https://docs.astral.sh/ruff/rules/ (full rules index, no `too-many-lines` entry)
  - Source: https://github.com/astral-sh/ruff/issues/970 (Pylint implementation tracker)
- `PLR0915 too-many-statements` exists in ruff but is **per-function**, not per-file. Default 50. Configured via `[tool.ruff.lint.pylint] max-statements = 50`.
  - Source: https://docs.astral.sh/ruff/rules/too-many-statements/

**Consequence for ChaosLab:** ruff cannot enforce the 400-line file limit. We use a pre-commit hook + CI check instead. Three viable mechanisms:

#### Option A (recommended) — custom pre-commit local hook

Add to `.pre-commit-config.yaml`:

```yaml
- repo: local
  hooks:
    - id: max-file-lines
      name: Enforce 400-line file limit
      entry: scripts/check_max_lines.py
      language: python
      types_or: [python, ts, tsx, javascript, jsx]
      exclude: |
        (?x)^(
          .*\.generated\..*|
          .*_pb2\.py|
          .*_pb2_grpc\.py|
          .*\.lock|
          poetry\.lock|
          package-lock\.json|
          pnpm-lock\.yaml|
          uv\.lock
        )$
```

`scripts/check_max_lines.py`:

```python
#!/usr/bin/env python3
"""Fail commit if any file exceeds MAX_LINES."""
from __future__ import annotations

import sys
from pathlib import Path

MAX_LINES = 400

def main(argv: list[str]) -> int:
    failures: list[tuple[str, int]] = []
    for arg in argv[1:]:
        p = Path(arg)
        if not p.is_file():
            continue
        # Count physical lines (matches what ruff/eslint count).
        with p.open("rb") as f:
            n = sum(1 for _ in f)
        if n > MAX_LINES:
            failures.append((arg, n))
    for path, n in failures:
        print(f"ERROR: {path} has {n} lines (limit {MAX_LINES})", file=sys.stderr)
    return 1 if failures else 0

if __name__ == "__main__":
    raise SystemExit(main(sys.argv))
```

Why a custom script instead of `awk`:

- Cross-platform (macOS/Linux/Windows CI).
- Easy to extend with per-language exemptions (e.g., autogenerated protobuf, migrations, lockfiles).
- Same script runs in CI on the whole tree, not just staged files: `find . -path ./node_modules -prune -o -name '*.py' -print | xargs ./scripts/check_max_lines.py`.

#### Option B — bash one-liner in CI only

For projects that don't want a Python script in the loop:

```bash
# .github/workflows/ci.yml — step "Enforce 400-line cap"
- name: Enforce 400-line cap
  run: |
    set -e
    fail=0
    while IFS= read -r f; do
      n=$(wc -l < "$f")
      if [ "$n" -gt 400 ]; then
        echo "::error file=$f::$f has $n lines (limit 400)"
        fail=1
      fi
    done < <(find . \
      -path ./node_modules -prune -o \
      -path ./.next -prune -o \
      -path ./.venv -prune -o \
      -path ./dist -prune -o \
      \( -name '*.py' -o -name '*.ts' -o -name '*.tsx' \
         -o -name '*.js' -o -name '*.jsx' \) -print)
    exit $fail
```

`wc -l` counts newlines; matches ruff/ESLint physical-line counting. [VERIFIED behavior, but edge case: a file without a trailing newline is undercounted by 1 — acceptable for a soft buffer.]

#### Option C — keep pylint just for C0302

You can run pylint _only_ for the `too-many-lines` rule. Not recommended because it adds a dependency and is slower than the bash hook, but documented for completeness:

```toml
# pyproject.toml
[tool.pylint.main]
disable = ["all"]
enable = ["too-many-lines"]
[tool.pylint.format]
max-module-lines = 400
```

Then `pylint src/` in CI. Source: https://pylint.readthedocs.io/en/stable/user_guide/messages/convention/too-many-lines.html

**ChaosLab decision: use Option A (pre-commit local hook) + Option B mirror in CI for double protection.**

### 1.2 TypeScript / JavaScript — ESLint `max-lines` (native)

ESLint ships the rule out of the box. Configuration:

```js
// eslint.config.mjs
rules: {
  'max-lines': ['error', {
    max: 400,
    skipBlankLines: true,
    skipComments: true,
  }],
}
```

- Default `max` is 300; we override to 400.
- `skipBlankLines: true` and `skipComments: true` align with the spirit of the rule (count logical code lines).
- Source: https://eslint.org/docs/latest/rules/max-lines

Note that ESLint's `max-lines` counts physical lines while our Python script counts all lines including blanks. For consistent enforcement across both stacks, we either:

- (a) Use `skipBlankLines: false, skipComments: false` in ESLint (strict — matches Python), or
- (b) Set `skipBlankLines: true, skipComments: true` (lenient — recommended). [UNVERIFIED whether ChaosLab cares — picking lenient default in spec.]

Companion rule worth enabling: `max-lines-per-function` (default 50). Source: https://eslint.org/docs/latest/rules/max-lines-per-function

### 1.3 Markdown / YAML / other

For docs and config, the same `check_max_lines.py` script handles `.md`, `.yml`, `.yaml`, `.json` with a higher threshold (markdown sometimes legitimately exceeds 400 lines — e.g., long ADRs). Recommended split:

| Glob                        | Limit |
| --------------------------- | ----- |
| `**/*.py`                   | 400   |
| `**/*.{ts,tsx,js,jsx}`      | 400   |
| `**/*.md`                   | 1000  |
| `**/*.{yml,yaml,toml,json}` | 600   |

[UNVERIFIED — these are pragmatic defaults; Abu can tighten.]

### 1.4 Other languages (Go, Rust)

Not in ChaosLab's stack, but documented for completeness:

- Go: `gocyclo` and `funlen` linters (functional, not file-level). For file-level: `golangci-lint` exposes `lll` (line length) and `gocognit`, no native file-line cap — same custom script approach. Source: https://golangci-lint.run/
- Rust: `clippy` has `too_many_lines` for functions (default 100). File-level enforced by external scripts. Source: https://rust-lang.github.io/rust-clippy/master/index.html#too_many_lines

### What `strict = true` enables

`strict = true` is a meta-flag. As of mypy 1.x it activates the following individual flags (verified via `mypy --help`):

- `warn_unused_configs`
- `disallow_any_generics`
- `disallow_subclassing_any`
- `disallow_untyped_calls`
- `disallow_untyped_defs`
- `disallow_incomplete_defs`
- `check_untyped_defs`
- `disallow_untyped_decorators`
- `no_implicit_optional`
- `warn_redundant_casts`
- `warn_unused_ignores`
- `warn_return_any`
- `no_implicit_reexport`
- `strict_equality`
- `extra_checks`

Source: https://mypy.readthedocs.io/en/stable/config_file.html
Source: https://typing.python.org/en/latest/spec/mypy.html

We additionally enable `warn_unreachable` (not in `strict`) because it catches real bugs in async control flow.

### Pydantic plugin

The `pydantic.mypy` plugin synthesizes `__init__` signatures so mypy understands model construction. Without it, every `MyModel(x=1, y=2)` is typed as `Any`.

- `init_forbid_extra = true` mirrors `model_config = ConfigDict(extra="forbid")` — extra kwargs at construction become type errors.
- `init_typed = true` makes the synthesized `__init__` strictly typed (vs. `Any`-wrapped). Recommended for strict mode.
- `warn_required_dynamic_aliases = true` errors when validators with dynamic aliases skip mypy verification.

Source: https://pydantic.dev/docs/validation/latest/integrations/dev-tools/mypy/

### Coverage target

100% type-annotated for `src/`. Enforce via mypy in CI plus an annotation coverage gate:

```bash
# CI step — annotation coverage
mypy src/ --html-report .mypy_report
python -c "import re,sys,pathlib; \
  html = pathlib.Path('.mypy_report/index.html').read_text(); \
  pct = float(re.search(r'(\d+\.\d+)%</td>\s*</tr>\s*<tr class=\"summary\">', html).group(1)); \
  sys.exit(0 if pct == 100.0 else 1)"
```

[UNVERIFIED — this HTML-parsing trick is brittle; consider `mypyc-coverage` or `interrogate` instead in production.] A more robust alternative is `interrogate` for docstring coverage and `mypy --strict` exit code for type coverage.

### Biggest mypy gotcha for ADK code

`google.adk` ships partial stubs in 2026; many decorator-heavy patterns (`@agent`, `@tool`, callback registrations) lose their type information after mypy walks through the decorator. Mitigation:

1. Add `ignore_missing_imports = true` for `google.adk.*` (above).
2. Annotate decorator-wrapped functions explicitly with `# type: ignore[misc]` only where strictly necessary.
3. Use `cast()` at API boundaries between ADK objects and your typed domain code.
4. Consider wrapping ADK primitives in your own Pydantic models inside `chaoslab.adk_types` — this gives mypy a fully-typed surface and quarantines the dynamic boundary.

## 4. pyright as alternative

`pyright` is Microsoft's type-checker — strictly faster than mypy on large projects, ships with Pylance for VS Code, and has a stricter default for inferred types.

```toml
# ============================================================
# pyright — alternative type checker
# Docs: https://microsoft.github.io/pyright/#/configuration
# ============================================================
[tool.pyright]
include = ["src", "tests"]
exclude = ["**/node_modules", "**/__pycache__", ".venv", "build", "dist"]
pythonVersion = "3.12"
pythonPlatform = "Linux"
typeCheckingMode = "strict"     # the headline switch
useLibraryCodeForTypes = true
reportMissingImports = "error"
reportMissingTypeStubs = "warning"
reportUnusedImport = "error"
reportUnusedVariable = "warning"
reportPrivateUsage = "warning"
reportUnknownMemberType = "warning"
reportUnknownArgumentType = "warning"
reportUnknownVariableType = "warning"
```

Source: https://microsoft.github.io/pyright/#/configuration (general structure verified; specific 2026 defaults [UNVERIFIED])

### mypy vs pyright — when to use which

| Dimension            | mypy                                  | pyright                                                |
| -------------------- | ------------------------------------- | ------------------------------------------------------ |
| Default strictness   | More lenient                          | Stricter                                               |
| Speed on large repos | Slower                                | Significantly faster                                   |
| Plugin ecosystem     | Mature (pydantic, sqlalchemy, django) | Limited (no plugins)                                   |
| Editor integration   | Via LSP                               | Native via Pylance                                     |
| Inference quality    | Good                                  | Excellent (often catches what mypy misses)             |
| Strict mode coverage | Configurable via `strict = true`      | `typeCheckingMode = "strict"`                          |
| CI footprint         | pip install                           | npm install or pip install pyright (wraps node binary) |

**ChaosLab recommendation:** mypy in CI (for the pydantic plugin), pyright in editors (for speed + better inference). Both should pass; differences in their output are usually genuine bugs.

[UNVERIFIED claim about pyright being stricter — this is widely repeated in the Python community but the exact rule overlap shifts release to release. Best to run both on a representative file and compare.]

### Why `singleQuote: true`, `semi: true`

The current 2026 community split:

- Single quotes in TS/JS: dominant in Next.js / Vercel / TypeScript-first projects.
- Double quotes in JSX attributes: matches HTML, less screen noise.
- Semicolons: still the default; only the Standard.js community drops them. Keeping semicolons avoids ASI-edge-case bugs.

## 9. Test naming + organization conventions

### File naming

- `test_<unit>.py` — preferred. Aligns with `pytest`'s default `python_files`.
- Mirror source layout: `src/chaoslab/foo/bar.py` → `tests/unit/chaoslab/foo/test_bar.py`.

### Test function naming

- `def test_<behavior>__when_<condition>__then_<expected>():` for readability
  - Example: `def test_run_workflow__when_agent_times_out__then_raises_timeout_error():`
- Or simpler: `def test_<behavior>():` if the body is self-documenting.

### Class vs function style

- **Function-based** is the default in modern pytest; classes only for grouping shared fixtures or parametrize matrices.
- If using classes: `class TestFooBehavior:` (no `unittest.TestCase` inheritance — kills pytest fixtures).

### Fixture placement

- `conftest.py` at the level where fixtures are needed.
- Root `tests/conftest.py`: global fixtures (event_loop, env setup).
- `tests/integration/conftest.py`: integration-only fixtures (Firestore emulator client, etc.).
- Per-module `conftest.py` only if shared across siblings.

### Directory split

```
tests/
├── conftest.py
├── unit/                    # fast, in-process, no I/O
│   └── chaoslab/...
├── integration/             # emulator / docker-compose / firestore-emulator
│   ├── conftest.py
│   └── chaoslab/...
├── e2e/                     # real Cloud Run, real ADK, real Firestore
│   └── workflows/
└── fixtures/                # static fixture data: JSON snapshots, fake configs
```

### Marker policy

| Marker        | Default in CI               | Why                       |
| ------------- | --------------------------- | ------------------------- |
| `unit`        | Always run                  | Cheap; gate on every PR   |
| `integration` | Run on PR + main            | Slower; emulators only    |
| `e2e`         | Nightly + on tag            | Real Cloud spend          |
| `slow`        | Skip in PR; run nightly     | Local iteration speed     |
| `online`      | Skip without `--run-online` | Avoid flaky external deps |

Invoke as: `pytest -m "unit or integration"`, `pytest -m "not slow"`, etc.

## 10. Type-safe schemas (pydantic v2)

### Why pydantic v2 over dataclasses for agent code

| Need                                   | dataclass     | pydantic v2                                                                        |
| -------------------------------------- | ------------- | ---------------------------------------------------------------------------------- |
| Runtime validation                     | No            | Yes (Rust-backed validators)                                                       |
| JSON (de)serialization                 | Manual        | `.model_dump_json()` / `.model_validate_json()`                                    |
| OpenAPI / FastAPI integration          | Hack          | Native                                                                             |
| Settings management                    | No            | `pydantic-settings`                                                                |
| Schema generation for LLM tool-calling | Manual        | `.model_json_schema()` — directly consumable by ADK / OpenAI / Anthropic tool defs |
| mypy support                           | Native        | Via plugin (described in §3)                                                       |
| Field-level validators                 | No            | Yes                                                                                |
| Computed fields                        | Property-only | `@computed_field` (serializable)                                                   |

For an agent project, pydantic v2 wins on the schema-generation axis alone: every tool / function-call definition can derive its schema directly from the model.

### Strict mode patterns

```python
from typing import Annotated
from pydantic import BaseModel, ConfigDict, Field, computed_field, field_validator

class ChaosScenario(BaseModel):
    model_config = ConfigDict(
        strict=True,            # no implicit coercion (str→int, etc.)
        extra="forbid",         # unknown keys = error
        frozen=True,            # immutable instances
        populate_by_name=True,  # accept both alias and field name
        validate_assignment=True,
        ser_json_timedelta="iso8601",
    )

    name: Annotated[str, Field(min_length=1, max_length=128)]
    blast_radius_pct: Annotated[float, Field(ge=0.0, le=1.0)]
    duration_s: Annotated[int, Field(ge=1, le=3600)]

    @field_validator("name")
    @classmethod
    def name_must_be_kebab(cls, v: str) -> str:
        if not v.replace("-", "").isalnum() or "_" in v:
            raise ValueError("name must be kebab-case")
        return v

    @computed_field  # serialized to JSON
    @property
    def severity(self) -> str:
        if self.blast_radius_pct >= 0.5:
            return "critical"
        return "moderate" if self.blast_radius_pct >= 0.2 else "low"
```

## 11. Logging standards

### Choice: structlog + stdlib logging

```python
# src/chaoslab/logging_config.py
import logging
import sys
import structlog
from chaoslab.config import Settings

def configure_logging(settings: Settings) -> None:
    is_tty = sys.stderr.isatty()
    timestamper = structlog.processors.TimeStamper(fmt="iso", utc=True)

    shared = [
        structlog.contextvars.merge_contextvars,
        structlog.stdlib.add_logger_name,
        structlog.stdlib.add_log_level,
        timestamper,
        structlog.processors.StackInfoRenderer(),
        structlog.processors.format_exc_info,
    ]

    if is_tty:
        renderer = structlog.dev.ConsoleRenderer(colors=True)
    else:
        renderer = structlog.processors.JSONRenderer()

    structlog.configure(
        processors=[*shared, renderer],
        wrapper_class=structlog.make_filtering_bound_logger(
            getattr(logging, settings.log_level)
        ),
        logger_factory=structlog.PrintLoggerFactory(file=sys.stderr),
        cache_logger_on_first_use=True,
    )
```

### Correlation IDs / Phoenix trace propagation

```python
import structlog
from opentelemetry import trace

def bind_trace_context() -> None:
    span = trace.get_current_span()
    ctx = span.get_span_context()
    if ctx.is_valid:
        structlog.contextvars.bind_contextvars(
            trace_id=format(ctx.trace_id, "032x"),
            span_id=format(ctx.span_id, "016x"),
        )
```

Every log line then carries `trace_id` and `span_id`, joinable against Phoenix spans. Source: https://www.structlog.org/en/stable/logging-best-practices.html

### Log levels per environment

| Env       | Console renderer | Level                |
| --------- | ---------------- | -------------------- |
| local dev | Color console    | DEBUG                |
| test      | JSON             | WARNING              |
| staging   | JSON             | INFO                 |
| prod      | JSON             | INFO (DEBUG on flag) |

### Standards

- **Never** log secrets — secret values must use `pydantic.SecretStr` and never be `str()`-ed in log calls.
- **Never** use string formatting in log calls. Use kwargs: `log.info("started", workflow=name)` not `log.info(f"started {name}")` — preserves structure + lazy evaluation.
- **Always** include a `trace_id` when inside a span.

## 12. Code review checklist

This rubric becomes the input to `sahil-pr-audit`.

### Correctness

- [ ] Behavior matches BDD acceptance criteria in the story.
- [ ] Edge cases handled (empty inputs, None, overflow, concurrent access).
- [ ] No off-by-one, dead branches, or unreachable code.
- [ ] Async code awaits everything; no fire-and-forget without explicit comment.

### Type safety

- [ ] mypy `--strict` passes with zero `# type: ignore` in new code (or each ignore has a comment + ticket link).
- [ ] No `Any` returned from public functions.
- [ ] Pydantic models use `strict=True` and `extra="forbid"` where appropriate.
- [ ] `TYPE_CHECKING` used for type-only imports.

### Security

- [ ] No hardcoded secrets (gitleaks must pass).
- [ ] User-controlled inputs validated before any system call.
- [ ] SQL / NoSQL queries parameterized.
- [ ] Subprocess calls use `shell=False` and explicit arg lists.
- [ ] Dependencies have no known critical CVEs (`pip-audit`, `npm audit`).

### Performance

- [ ] No O(n²) where O(n log n) suffices for n>1k.
- [ ] DB queries: no N+1, indexes used, batched where possible.
- [ ] Async I/O used for any network call inside a request handler.
- [ ] Hot loops have no avoidable allocations.

### Testability + tests

- [ ] New code has unit tests; integration tests where it crosses a system boundary.
- [ ] Coverage delta is positive or coverage stays ≥80% in this module.
- [ ] Tests use markers correctly (`@pytest.mark.unit` etc.).
- [ ] No flaky / time-dependent assertions (`freezegun` or fake clocks for time).

### Naming + readability

- [ ] Names are kebab/snake/Pascal per language convention.
- [ ] No abbreviations except universal ones (id, url, db).
- [ ] Functions ≤80 lines (warn) / 50 statements (error).
- [ ] Files ≤400 lines (hard limit).

### Error handling

- [ ] No bare `except:` and no `except Exception` without explicit re-raise or logging.
- [ ] Exceptions carry useful context (no `raise ValueError("bad")`).
- [ ] Resources released via `with` / `try/finally` / async context managers.

### Observability

- [ ] Critical paths log structured events with `trace_id`.
- [ ] Metrics emitted for SLO-relevant events.
- [ ] Span attributes added for new operations.

### Frontend (TS only)

- [ ] No `any` in TS source.
- [ ] React Server Components used unless interactivity required.
- [ ] No dynamic imports without explicit reason.
- [ ] Tailwind classes use semantic groupings; no inline `style=` unless dynamic.
- [ ] Accessibility: alt text, aria labels, keyboard navigation.

## 13. Conventional commits

### Format

```
<type>[(scope)]: <subject>

[optional body]

[optional footer(s)]
```

- Subject: imperative mood, ≤72 chars, no period.
- Body: wrap at 80 cols, blank line after subject.
- Footers: `Key: Value` or `Key #value`. Use hyphens, not spaces.

### Types

| Type       | Meaning                                         | SemVer  |
| ---------- | ----------------------------------------------- | ------- |
| `feat`     | New end-user feature                            | MINOR   |
| `fix`      | Bug fix                                         | PATCH   |
| `docs`     | Documentation only                              | none    |
| `style`    | Formatting / whitespace; no behavior change     | none    |
| `refactor` | Code change that is neither a fix nor a feature | none    |
| `perf`     | Performance improvement                         | PATCH   |
| `test`     | Adding or fixing tests                          | none    |
| `chore`    | Routine task (config bumps)                     | none    |
| `ci`       | CI config changes                               | none    |
| `build`    | Build system / external deps                    | none    |
| `revert`   | Reverts a previous commit                       | depends |

Source: https://www.conventionalcommits.org/en/v1.0.0/

### Scope

A noun describing the affected area: `feat(orchestrator):`, `fix(adk-bridge):`, `docs(architecture):`.

### Breaking change marker

Two equivalent forms:

1. `feat!: drop support for Python 3.10`
2. Footer: `BREAKING CHANGE: agent signature now requires async context`

Either marks the commit as MAJOR-bump in semver.

### Automatic changelog

- `git-cliff` (Rust) or `conventional-changelog` (Node) parse commit history into CHANGELOG.md.
- ChaosLab decision: `git-cliff` via a GitHub Action on tag push. [UNVERIFIED — alternative is `commitizen` which combines bump + changelog.]

### Enforcement

- Pre-commit `commit-msg` hook: `conventional-pre-commit` (above) blocks bad commit messages locally.
- CI: a job runs `commitlint` against all commits in the PR.
  ```yaml
  - uses: wagoid/commitlint-github-action@v6
  ```
